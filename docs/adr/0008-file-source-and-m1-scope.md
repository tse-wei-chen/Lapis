# ADR-0008 — M1 FileSource, timebase and FFmpeg boundary

- Status: Accepted for incremental implementation (2026-10-20).
- `FileSource` is an adapter in `native/.../src/adapters/file`, not a Core or C ABI type. It provides read-at-offset operations and observable status, with a mutex guarding the reusable `std::ifstream`. It does not yet provide asynchronous I/O/cancellation, source fingerprints, remote URLs, file watchers, or a buffer pool. A caller controls each read buffer size.
- Local plain UTF-8 paths and `file:///` URIs are accepted; `file://localhost/` is local. Remote hosts and URL query/fragment are rejected; percent escape decoding is checked. Windows drive paths are handled as a platform detail inside the adapter. This is **not** security hardening for untrusted paths or Flatpak access; open must follow user-granted file-picker/portal paths at application layer.
- `core/media_time.hpp` converts rational PTS to ns with checked arithmetic; it rejects ratios/inputs whose intermediate or output integer math cannot be represented (no silent overflow). FFmpeg's future time-base migration must preserve NOPTS semantics and source timestamps separately; a `std::nullopt` must not be silently treated as timestamp zero.
- `core/PlaybackClock` takes a caller-supplied monotonic nanosecond tick. It is only a monotonic-clock baseline. Audio-master/decoder latency accounting will be required for actual playback.
- `EpochQueue` rejects messages from incorrect SessionId/Epoch and has capacity/drop policies. Producers are **not guaranteed lock-free**; it uses short mutex critical sections, not suitable for a hard realtime audio callback. Actual audio callbacks will require a dedicated realtime-safe SPSC queue or preallocated ring.
- The `tools/ffmpeg_media_diagnostic.py` script validates installed FFmpeg command-line tools can decode generated MP4/MKV fixtures and produce RGB and PCM bytes; it is **not** a part of MediaRuntime, not a decoder implementation, not real-time A/V sync and not playable GUI output. No FFmpeg headers/dev libraries are installed in the current verification container. We will integrate the libavformat/libavcodec libraries in an adapter once a build environment with the dev packages exists.
- Keep `bdmv_session_open_uri(file://...) == BDMV_UNSUPPORTED` and `engine_capabilities.file_source == 0` until the file adapter is connected to an actual demux/decode media graph. Advertising playable file formats from the existence of a byte reader would be misleading.
- `BDMV_ABI_MAJOR/MINOR` and C structs unchanged in this increment; no P/Invoke contract change.
